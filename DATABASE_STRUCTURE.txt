# SECTION 4: LOGIN & AUTHENTICATION FLOW
# ============================================================

## Customer Login Flow:
  1. User enters email address
  2. System checks Firestore "users" collection
  3. If user exists and role is "customer":
     a. Generate 4-digit OTP (crypto.randomInt)
     b. Store OTP in "otp_store" collection (expires in 5 min, max 5 attempts)
     c. Send OTP via email (nodemailer/SMTP)
     d. Show OTP input screen
  4. User enters OTP
  5. System verifies OTP against Firestore:
     a. Check not expired
     b. Check attempts < 5
     c. Check OTP matches
  6. On success:
     a. Create/update user record in "users" collection
     b. Auto-assign canteen from user's collegeId (first active canteen)
     c. Return user object with role, collegeId, canteenId
  7. Session persisted in localStorage:
     - bb_user: full user object
     - bb_role: role string
     - bb_loggedIn: "true"
     - bb_orders: cached orders

## Owner/Chef/Staff/Admin Login Flow:
  1. User enters email + password
  2. System checks Firestore "users" collection
  3. If user exists and password matches (bcrypt compare):
     a. Return user object with role, canteenId, subCanteenId
  4. If user doesn't exist:
     a. Auto-create default user with "customer" role
     b. Return error (must register properly)
  5. Session persisted same as customer

## Superadmin Login Flow:
  1. Same as owner/chef/staff login
  2. Pre-seeded in Firestore with email/password
  3. Role = "superadmin" grants access to all features

# SECTION 5: ORDER PLACEMENT WORKFLOW
# ============================================================

## Online Order Flow:
  1. Customer browses menu (filtered by collegeId/canteenId)
  2. Adds items to cart (client-side state)
  3. Selects pickup slot (e.g. "12:30-12:45")
  4. Clicks "Place Order"
  5. Server validates:
     a. All items in stock
     b. Daily limit not exceeded
     c. Pickup slot not full (based on settings.defaultSlotCapacity)
     d. Ingredients available
  6. Payment:
     a. Paytm: Server generates checksum -> client POSTs form -> Paytm gateway
        -> Paytm calls back /api/paytm/callback -> server verifies -> redirect
     b. Mock: Server creates order directly with status "paid"
  7. On payment success:
     a. Order created in "orders" collection
     b. Item stock decremented, bookedToday incremented
     c. Ingredient stock decremented
     d. qrPayload (signed HMAC) stored with order
     e. Order returned to client with QR code
  8. Customer sees order in "Order History" tab with QR code

## Walk-in Order Flow (POS):
  1. Cashier (owner/staff) opens Walk-in POS
  2. Adds items to walk-in cart
  3. Enters customer details (optional)
  4. Selects payment method (cash/upi/card/etc.)
  5. Creates walk-in bill in "walkin_bills" collection
  6. Optionally creates corresponding order in "orders" collection
  7. Bill stored locally, synced to Firestore

## Order Status Flow:
  pending -> preparing -> ready -> collected
  pending -> cancelled (by staff/chef)
  pending -> expired (after noShowMinutes timeout)

  Status updates:
  - Owner/Chef: Can set preparing, ready, cancelled
  - Staff: Can set collected
  - Customer: Can view status in real-time


# ============================================================
# SECTION 6: QR CODE VERIFICATION WORKFLOW
# ============================================================

  1. When order is placed, server generates qrPayload:
     - HmacSHA256(orderId + "|" + timestamp + "|" + secret, SECRET_KEY)
     - Base64 encoded
  2. Customer sees QR code in Order History tab
  3. Staff scans/verifies QR:
     a. GET /api/canteen/qr/verify?qr=<payload>
     b. Server decodes payload, checks HMAC signature
     c. Checks order exists and is "ready" status
     d. Returns order details
  4. Staff confirms pickup:
     a. POST /api/canteen/qr/verify with body {qr, action: "collect"}
     b. Order status updated to "collected"
  5. Backfill: Server auto-generates qrPayload for old orders missing it

# ============================================================
# SECTION 12: PAYMENT FLOW (PAYTM)
# ============================================================

  1. Customer places order -> Client calls POST /api/canteen/order
  2. Server generates unique orderId, creates order in Firestore (status=pending)
  3. Server generates Paytm checksum (HMAC SHA256) with merchant credentials
  4. Server returns checksum + Paytm params to client
  5. Client creates hidden HTML form, auto-submits to Paytm gateway
  6. Customer completes payment on Paytm page
  7. Paytm redirects back to app OR calls /api/paytm/callback
  8. Server verifies checksum, updates order status:
     - Transaction successful: paymentStatus="paid", updates item stock/ingredients
     - Transaction failed: paymentStatus="failed"
  9. Order confirmation shown to customer

  Environment Variables:
    PAYTM_MERCHANT_ID    - Paytm merchant ID
    PAYTM_MERCHANT_KEY   - Paytm merchant secret key
    PAYTM_MERCHANT_WEBSITE - Paytm website name
    PAYTM_ENVIRONMENT    - "staging" or "production"
    PAYTM_CALLBACK_URL   - Server callback URL

  - QR payload = HMAC SHA256 signed string (not actual QR image)
  - Orders auto-expire after noShowMinutes (default 30 min)
