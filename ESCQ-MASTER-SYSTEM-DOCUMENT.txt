2. EXECUTIVE SUMMARY
============================================================

Esc(Q) is a full-stack smart canteen management platform that
digitizes the campus food ordering experience. Students order
via a mobile app, pay online (Razorpay or UPI), receive a QR
ticket, and collect food at the counter -- eliminating queues.

The system spans three client surfaces:
  1. Flutter Mobile App (Android/iOS) -- primary customer app
  2. React Web App (SPA) -- admin/staff/owner dashboard + customer web
  3. Capacitor Android -- web app wrapped as native Android

The backend is a TypeScript Express.js monolith deployed as a
Vercel serverless function, backed by Supabase PostgreSQL.

9. FRONTEND ARCHITECTURE
============================================================

--- FLUTTER MOBILE APP ---

Architecture Pattern: Feature-based folder structure
  models/ -> providers/ -> screens/ -> services/
  No formal clean architecture (MVVM/MVC).

State Management: Provider (ChangeNotifier)
  5 Providers:
    AuthProvider    -- login, register, logout, session
    MenuProvider    -- colleges, canteens, items, filtering
    CartProvider    -- cart items, pricing calculations
    OrderProvider   -- order placement, history, reviews
    ThemeProvider   -- dark/light toggle, persistence

Navigation: Imperative Navigator
  - Navigator.push / pushReplacement / pushAndRemoveUntil
  - onGenerateRoute for /legal/* routes only
  - Entry point: AppEntryPoint (splash -> auth gate -> home/staff)

Data Flow:
  User Action -> Screen (StatefulWidget)
    -> Provider method -> ApiService (HTTP)
    -> Express backend -> PostgreSQL
    -> Response -> Provider state update -> UI rebuild

--- REACT WEB APP ---

Architecture: Single-file SPA (App.tsx as root router)
  - Role-based view switching in App.tsx
  - Components organized by feature
  - No formal state management library (React useState/useEffect)

Navigation: Custom SPA routing
  - window.history.pushState + popstate listener
  - Routes: / (main), /download, /support
  - No React Router

Data Flow:
  User Action -> Component (useState)
    -> fetch() with JWT interceptor (config.ts)
    -> Express backend -> PostgreSQL
    -> Response -> setState -> UI re-render

10. BACKEND ARCHITECTURE
============================================================

Framework:     Express.js 4.21.2 (TypeScript)
Entry Point:   server.ts (4454 lines, monolithic)
Database:      PostgreSQL via pg driver (no ORM)
Deployment:    Vercel serverless function

Pattern:       Single-file monolith
  - All routes defined in server.ts
  - All middleware in server.ts
  - Business logic inline in route handlers
  - No separate controller/model files

Key Architectural Decisions:
  1. Firestore-compatible helpers over raw SQL (db.ts)
  2. In-memory state fallback when PostgreSQL unavailable
  3. Schema introspection (discovers columns at runtime)
  4. camelCase <-> snake_case auto-conversion
  5. Request-triggered background jobs (no cron scheduler)

Middleware Stack:
  1. CORS (whitelist-based)
  2. Body parser (10MB limit)
  3. Rate limiter (30 req/min/IP)
  4. Security headers
  5. Auth (Supabase JWT verification)
  6. Role-based access (superadmin/management)
  7. PostgreSQL readiness check
  8. Vercel path rewriting

11. DATABASE ARCHITECTURE
============================================================

Database:      PostgreSQL (Supabase-hosted)
Driver:        pg (node-postgres) v8.23.0
Connection:    Pool with 10 max connections, 30s idle timeout
SSL:           Required (rejectUnauthorized: false)
No ORM:        Custom helper layer in db.ts

--- DATABASE HELPER LAYER (db.ts) ---

Provides Firestore-like helpers over raw SQL:

| Helper                    | SQL Operation                          |
|---------------------------|----------------------------------------|
| query(text, params)       | Raw SELECT -> rows[]                   |
| queryOne(text, params)    | Raw SELECT -> first row                |
| execute(text, params)     | INSERT/UPDATE/DELETE -> row count       |
| pgGetById(table, id)      | SELECT * WHERE pk = $1                 |
| pgGetAll(table)           | SELECT * FROM table                    |
| pgGetWhere(table, conds)  | SELECT * WHERE col1=$1 AND col2=$2     |
| pgSet(table, id, data)    | INSERT ... ON CONFLICT DO UPDATE       |
| pgUpdate(table, id, data) | UPDATE SET col=$1 WHERE pk=$2          |
| pgDelete(table, id)       | DELETE WHERE pk = $1                   |
| pgDeleteWhere(table, conds)| DELETE WHERE col1=$1                   |
| pgIncrement(table, id, col, amt)| UPDATE SET col = col + $1      |
| pgGetByEmail(table, email)| SELECT WHERE email = $1                |

Schema Introspection:
  - On first write to a table, queries information_schema.columns
  - Discovers real column names at runtime
  - Filters out fields not present in DB (drift safety)
  - Caches column sets per table

Case Conversion:
  - All JS data: camelCase -> snake_case before DB storage
  - All DB results: snake_case -> camelCase before returning

Primary Key Map:
  - Most tables: 'id'
  - settings table: 'canteen_id'
  - otp_store table: 'email'

14. AUTHENTICATION
============================================================

[CONFIRMED from server.ts and auth_provider.dart]

Provider: Supabase Auth (email + password)

--- REGISTRATION ---
1. Client sends: name, email, password, phone, registerNumber, collegeId
2. Server validates (email format, password min 6 chars, unique email)
3. Creates user in Supabase Auth via supabaseAdmin.auth.admin.createUser()
   with email_confirm: true (auto-verified)
4. Waits 500ms for database trigger to create public.users profile
5. Signs in to get access_token and refresh_token
6. Returns tokens + user profile to client

--- LOGIN ---
1. Client sends: email, password
2. Server calls supabaseClient.auth.signInWithPassword()
3. Looks up public.users profile
4. SUPERADMIN SPECIAL FLOW: If email matches SUPERADMIN_CHECK_EMAIL,
   signs out and returns { pendingOtp: true } (requires OTP step)
5. For regular users: returns access_token + refresh_token + profile
6. Client stores tokens in SharedPreferences (Flutter) or
   localStorage (web): bb_token, bb_refresh_token

--- OTP FLOW (Superadmin Only) ---
1. POST /api/auth/generate-otp -- generates 6-digit code
2. Stores in otp_store table (email PK, 5-minute expiry)
3. Emails OTP via Resend API
4. POST /api/auth/verify-otp -- verifies code against stored OTP
5. If valid: creates Supabase session, returns tokens

--- SESSION MANAGEMENT ---
- No server-side session store (stateless JWT)
- Supabase access_token used for authenticated requests
- Client auto-refreshes token when < 60s to expiry
- On 401: client attempts refresh once, then hard reset
- Flutter: session persisted in SharedPreferences (bb_user JSON)

--- JWT VERIFICATION (authMiddleware) ---
1. Extracts Bearer token from Authorization header
2. Calls supabaseClient.auth.getUser(token)
3. If valid: attaches req.authUser, req.authEmail to request
4. If invalid: returns 401 Unauthorized

19. PAYMENT WORKFLOW
============================================================

--- RAZORPAY FLOW ---
1. Server creates Razorpay order via razorpay.orders.create()
   - Amount in paise (INR)
   - Receipt: order ID
   - Amount includes reverse-calculated processing fee
2. Client opens Razorpay SDK with order options
3. User completes payment in Razorpay UI
4. Razorpay returns: orderId, paymentId, signature
5. Client calls POST /api/razorpay/verify
6. Server verifies HMAC-SHA256: HMAC(orderId|paymentId, secret)
7. If signature mismatch: fallback to Razorpay API query
8. On success: fulfillRazorpayOrder()
   - Deducts item stock
   - Increments bookedToday
   - Deducts recipe ingredients
   - Sets order status to 'scheduled' or 'ready'
9. Client receives success, displays QR ticket

--- VYAPARGATEWAY (UPI QR) FLOW ---
1. Server creates transaction via VyaparGateway API
   - Auth: Basic base64(merchantId:secret) + X-Api-Key
   - Returns: qr_url, upi_string, transaction_id
2. Client displays UPI QR code image
3. User scans with any UPI app
4. Client polls order status every 1 second
5. Server webhook (POST /api/vyapar/webhook) confirms payment
6. On success: deducts stock, marks paid

--- AUTO-RECONCILIATION ---
- Triggered on every GET /api/user/orders call
- Any PENDING order with razorpayOrderId is checked against Razorpay API
- If captured payment found: auto-fulfills order
- Prevents "money deducted but order stuck" scenario

--- DUPLICATE PAYMENT PROTECTION ---
- Razorpay: signature verification prevents replay
- VyaparGateway: transaction ID uniqueness
- Order status check: only 'pending' orders can be fulfilled


============================================================
20. QR TICKET WORKFLOW
============================================================

--- GENERATION ---
1. On order fulfillment (payment verified)
2. Server calls generateSignedQR(orderId):
   - timestamp = Date.now()
   - signature = HMAC-SHA256(orderId.timestamp, QR_SECRET)
   - payload = JSON.stringify({ o: orderId, t: timestamp, s: signature })
3. payload stored as order.qrPayload in database
4. Client displays via QrImageView (qr_flutter package)
   - version: QrVersions.auto
   - size: 140-190px

--- DATA ENCODED ---
{
  "o": "ORD_1234",      // Order ID
  "t": "1234567890",    // Generation timestamp
  "s": "abcdef..."      // HMAC-SHA256 signature
}

--- VERIFICATION (Staff Scan) ---
1. Staff opens StaffHomeScreen -> Scanner tab
2. MobileScanner detects QR code via camera
3. Client calls GET /api/canteen/qr/verify?code={payload}
4. Server parses JSON payload
5. Recomputes HMAC and compares with provided signature
6. Looks up order in PostgreSQL
7. Returns order details to staff
8. Staff sees order details dialog with "Mark Served" button

--- COLLECTION ---
1. Staff taps "Mark Served"
2. Client calls POST /api/canteen/qr/verify with { code, action: 'collect' }
3. Server verifies signature again
4. Checks order status (must be 'ready')
5. Updates order status to 'collected'
6. Returns success with alreadyCollected flag for duplicate protection
7. QR is effectively invalidated (order is collected)

--- SECURITY ---
- HMAC-SHA256 prevents QR forgery
- QR_SECRET from environment variable (auto-generated if not set)
- Each QR is tied to specific order ID + timestamp
- Signature verification on every scan
- Duplicate scan protection via alreadyCollected flag

21. ORDER STATUS STATE MACHINE
============================================================

[CONFIRMED from code]

States:
  pending    -- Order created, payment not yet verified
  scheduled  -- Payment verified, awaiting preparation
  preparing  -- Kitchen actively preparing
  ready      -- Prepared, awaiting pickup
  collected  -- Customer collected (terminal)
  expired    -- Not picked up in time (terminal)
  cancelled  -- Cancelled by user/staff (terminal)
  delivered  -- (defined in types, not actively used)

State Transitions:

  [Order Created]
       |
       v
    pending ----(payment failed/cancelled)----> cancelled
       |
       | (payment verified, requiresChef=true)
       v
    scheduled ----(no-show expiry)----> expired
       |
       | (staff: "Start Preparing")
       v
    preparing
       |
       | (staff: "Mark Ready" OR requiresChef=false auto-ready)
       v
    ready ----(expiryTime passed)----> expired
       |
       | (staff: "Mark Collected" via QR scan)
       v
    collected

Who Can Change Each State:
  pending -> scheduled:   Server (on payment verification)
  pending -> ready:       Server (if requiresChef=false)
  pending -> cancelled:   Server (on payment failure)
  scheduled -> preparing: Staff/Owner (via order status update)
  preparing -> ready:     Staff/Owner/Chef (via order status update)
  ready -> collected:     Staff (via QR scan "Mark Served")
  ready -> expired:       Server (auto-expiry check on GET /api/canteen)
  Any -> cancelled:       Staff/Owner (manual cancellation)

Database Updates:
  - status field updated
  - prep_start_time set when entering 'preparing'
  - expiry_time calculated from pickup slot + noShowMinutes setting
  - Payment fields populated on payment verification

--- BACKEND ---
1. Global error handler (Express error middleware)

   - Adding item from different canteen throws CartCanteenMismatchException

   - Resets daily (server-side, mechanism not explicit)

   - Item stock decremented on order fulfillment
   - Orders rejected if stock insufficient
   - Ingredient stock also tracked and checked

   - Each pickup time slot has max capacity (default: 30)
   - Slot capacity checked during order placement

5. PLATFORM FEE
   - Convenience Fee: ceil(subtotal / 100)
   - PG Charge: (subtotal / 0.9764) - subtotal (reverse 2.36% processing fee)
   - Included in backend-calculated total

6. ORDER EXPIRY
   - Ready orders expire after noShowMinutes (default: 30 min)
   - Expiry checked on GET /api/canteen request

7. PAYMENT FIRST
   - QR code only generated after payment verified
   - Stock only deducted on payment verification (not on order creation)
   - Pending orders exist in DB but are not fulfilled

8. QR ONE-TIME USE
   - QR effectively invalidated after collection
   - Duplicate scan protection via alreadyCollected flag

9. ROLE RESTRICTION ON MOBILE
   - admin, superadmin, owner roles blocked from Flutter login
   - "This account is for web admin only"

10. PROFILE EDIT LOCAL ONLY
    - Profile changes save to SharedPreferences only
    - Server sync pending (not implemented)

11. WALK-IN BILLING
    - Creates records in both walkin_bills and orders tables
    - Can be paid immediately or marked pending
    - Bill number used as QR code

41. IMPORTANT IMPLEMENTATION DECISIONS
============================================================

1. SINGLE-FILE BACKEND (server.ts)
   - All 4454 lines in one file
   - Enables simple Vercel serverless deployment
   - Creates maintenance challenges

2. NO ORM -- RAW SQL
   - Custom Firestore-compatible helpers
   - Schema introspection for drift safety
   - More control but more boilerplate

3. BASE64 IMAGE STORAGE
   - No file upload/storage service
   - Server-side compression via sharp
   - Simpler but increases DB size

4. PROVIDER STATE MANAGEMENT (Flutter)
   - Simple, built-in Flutter solution
   - No complex state management overhead
   - 5 providers for 5 feature domains

5. POLLING OVER WEBSOCKETS
   - Simpler implementation
   - Works with serverless (no persistent connections)
   - Higher latency, more bandwidth

6. HMAC-SIGNED QR CODES
   - Prevents QR forgery
   - Server-side verification
   - No third-party QR service needed

7. AUTO-RECONCILIATION ON POLL
   - Handles "money deducted but order stuck" automatically
   - Triggered passively on user actions
   - No background worker needed

8. SUPABASE AUTH + RAW PostgreSQL
   - Auth via Supabase managed service
   - Database via raw SQL (not Supabase client)
   - Hybrid approach for flexibility

9. IN-MEMORY FALLBACK
   - System degrades gracefully when PostgreSQL unavailable
   - Data loss risk in serverless environment
   - Useful for development/testing

10. MONOLITHIC CLIENT + SEPARATE FLUTTER APP
    - React SPA for web (admin/staff/customer)
    - Flutter for native mobile (customer/staff)
    - Shared backend API
    - Some feature parity gaps between clients

PHASE 4: AI DEMAND & WASTE INTELLIGENCE
============================================================

--- 1. DEMAND PREDICTIONS ---

  Endpoint: POST /api/analytics/generate-predictions
  Method:
    - Aggregates historical order data (configurable lookback)
    - Calculates item-level daily averages
    - Applies 15% buffer for safety stock
    - Uses Gemini AI for intelligent forecasting (if configured)
    - Falls back to rule-based predictions

  Storage: demand_predictions table
    - Stores prediction date, confidence, and based-on-days

--- 2. WASTE TRACKING ---

  Endpoint: POST /api/waste/log
  - Log individual waste events with item, quantity, reason, cost

  Endpoint: GET /api/waste/summary
  - 30-day (configurable) waste summary
  - Breakdown by reason and by item
  - Total cost and quantity metrics

--- 3. AI RECOMMENDATIONS ---

  Endpoint: POST /api/recommendations/generate
  - Analyzes order patterns, waste data, ratings, and stock levels
  - Uses Gemini AI for intelligent recommendations (if configured)
  - Falls back to rule-based recommendations
  - Types: efficiency, waste, customer_satisfaction, cost
  - Priority: low, medium, high

--- 4. NEW DATABASE TABLES (Phase 4) ---

  demand_predictions:
    - Stores prediction results with confidence scores
    - Indexed by canteen_id and prediction_date

  demand_prediction_items:
    - Item-level prediction details (per-prediction)

  waste_records:
    - Individual waste event records
    - Indexed by canteen_id and item_id

  ai_recommendations:
    - AI-generated actionable recommendations
    - Indexed by status for active recommendation queries

PHASE 6: OFFLINE & NETWORK RESILIENCE

--- 1. OFFLINE SYNC SERVICE (Flutter) ---

  File: escq_canteen/lib/services/offline_sync_service.dart

  Features:
  - Queues write operations when offline
  - Auto-syncs when connectivity restores
  - Periodic sync attempts every 30 seconds
  - Conflict detection on sync
  - Persistent queue via SharedPreferences
  - Max retry limit (5 attempts) with failure marking

--- 2. OFFLINE INDICATOR WIDGET ---

  File: escq_canteen/lib/widgets/offline_indicator.dart

  Features:
  - Real-time online/offline status display
  - Pending sync count indicator
  - Manual sync trigger button
  - Integrated into HomeScreen and StaffHomeScreen

--- 3. SYNC API ENDPOINTS ---

  POST /api/sync/push
    - Push offline changes to server
    - Conflict detection on order updates
    - Supports: order create/update, review create, waste create

  GET  /api/sync/pending
    - Get pending sync operations for a user

  POST /api/sync/resolve-conflict
    - Resolve detected conflicts
    - Choose local or remote version

  GET  /api/sync/conflicts
    - Get unresolved conflicts

  GET  /api/sync/events
    - Get sync event history

--- 4. NEW DATABASE TABLES (Phase 6) ---

  sync_queue:
    - Client-side offline operation queue
    - Tracks attempts, status, and last error

  synchronization_events:
    - Server-side sync event log
    - Tracks direction, entity type, conflict status

  conflict_records:
    - Detected data conflicts between local and remote
    - Stores both versions for resolution
